1) Finir le backend “API minimale réelle” (Étape 4)
Pourquoi : c’est le socle. Le front et Docker dépendent d’une API stable (même minimale).
→ Donc on fait : modèle + serializer + viewset + router (Message CRUD).
Ensuite commit + push.
2) Ajouter l’admin + .env.example + requirements.txt figé
Pourquoi : ça prépare l’industrialisation (config, dépendances, variables).
→ Commit + push.
3) Dockeriser backend + Postgres + docker-compose (sans frontend)
Pourquoi : on valide d’abord la stack backend+db dans Docker, c’est le plus “risqué” (réseau, migrations, env).
→ Commit + push.
4) Initialiser le frontend Vue 3 + Nginx (dockerisé)
Pourquoi : une fois l’API stable et dockerisée, le front devient simple (consommer /api/ via Nginx).
→ Commit + push.
5) CI/CD
Pourquoi : quand build docker compose est stable, tu automatises build/push/deploy.

Le serveur que tu lances avec python manage.py runserver est le serveur de développement Django.
Il sert à tester localement.
Il n’est pas fait pour la production (tu as vu l’avertissement).
En production, on remplacera runserver par :
Gunicorn (WSGI server)
derrière Nginx

En prod, / sera servi par Nginx (frontend Vue), et Django ne gèrera que /api/.
Tu peux (et tu dois) avoir HTTPS pour les deux :
danielgarcia.it
marketech.danielgarcia.it
Le reverse proxy peut gérer automatiquement les certificats avec Let’s Encrypt (via Traefik ou Nginx + certbot). C’est une pratique standard.
